# 設計レビュー：小さく保つ核と、まだ混ざっている責務

2026-09-13。確認開始点は `1225b95`（パッケージ0.5.0）の設計・検証記録です。そこから v0.6 の実装契約（保存、公開操作、索引、評価、パッキング、認可・削除、Memory/SQLite、研究コード）へ更新しました。運用中の全データを監査した結果ではありません。既存の数値・意味評価は、明記したものを v0.5 の研究ベースラインとして保持します。

**結論：Atomの表現と保存境界は維持する。v0.6の実行時評価は、本文一致・利用活性・構造伝播を `a = D(h)m + Tᵀa` の一つの線形解へ統合する。Schur消去と `research/composition/reference-ranking.mjs` に凍結した v0.5 参照実装は研究用に残し、runtimeへは採用しない。**

## 一文で定める核

> 情報と関係を版付きで保存し、文脈に必要な本文を、その解釈に必要な条件と出典とともに予算内で返す。

「必要な解像度まで読む」は、この契約を実現する読み出し方針です。「計算を合成・再利用する」は、それを実現する評価器の候補です。後者が不利なデータでも、Atom Memoryの意味が変わらない構成を保ちます。

Atomは唯一の最小意味単位を数学的に定義するものではなく、独立に参照・改訂できる情報の単位です。本文・まとまり・関係を同じ形式で表すことは、それらを同じ確率、同じ役割、同じ返却価値で扱うことではありません。

## 1. 関連度の順位を、そのまま返却価値にしている

`src/client/memory.ts` の `retrieve/search/read`、`src/client/ranking.ts` の `finishRanking`、`src/client/retrieval.ts` の `pack/createPacking` が境界です。

v0.6のruntimeは候補グラフを固定してから、本文一致 `m` と利用状態 `h` から `b = D(h)m` を作り、`a = b + Tᵀa` を解きます。高順位の説明Atomが大きなリンク一覧を持っていると、その説明とメタデータがコンテキスト予算を占めます。構造上よく接続された入口であることと、今回詳しく返すべき本文であることを区別できない点は、返却集合の評価課題として残ります。

`research/composition/semantic-results.json` の v0.5研究ベースラインでは、日本語の合成資料97 Atom・6問・実埋め込み・8192 byte-tokenの条件で、広いseedと64 seedは必要な根拠範囲を6問とも返せず、同じグラフの8 seedでは6問とも返しました。説明Atomが枠を占める出力が記録されています。これは小さな同作者の評価で、独立したWriter評価でも本番設定の評価でもありません。8を普遍的な正解にする根拠にはしません。

**改善の判断：探索に使う関連度と、本文集合を選ぶ目的を区別する。** 親を低くする固定分類や、sourceだけを優遇する必須ルールは導入しません。親の本文自体が答えになる場合も、出典を持たない有用な仮説を読む場合もあります。

次の評価では、返却集合を `S`、必須条件を含む閉包を `C(S)`、実際のシリアライズ費用を `cost(C(S))` とし、この費用が予算以内であることを共通条件にします。現在の順位greedyを基準に、追加本文・引用範囲・必要な関係がもたらす寄与を測ります。集合の価値関数、単調性、近似最適性は未定義で、既に証明したとはしません。トークン当たりscoreや意味的な重複判定を新しい既定値として足す前に、同じ条件で比較します。

## 2. 通常の関係が削除依存にもなっている

`src/core/store.ts` の `purge` とSQLiteの `purgePlan` は、出典・receiptだけでなく、すべてのリンクを逆向きにたどって所有Atomを削除します。

再現例は `P → B`、`Q → B`、`R → P` です。すべて単なる `related` リンクでも、BをpurgeするとB/P/Q/Rが消えます。無関係なUは残ります。Memory/SQLiteの両方で確認しました。あらゆる連結成分が必ず消えるという意味ではなく、歴史版も含めた逆依存の閉包です。

この規則は現在の保守的な削除保証と整合しています。しかし、関連があることと、本文がそこから作られたことを同一視しています。共有・長期構造が育つほど、削除の影響を広げます。

**改善の判断：次の削除契約では、関連の到達可能性と、本文の導出依存を区別する。** 単にslotを削除閉包から外す変更は行いません。古い本文に参照対象の内容が含まれる可能性があり、リンク先が消えた後の `view/inspect` も現在は失敗するためです。導出記録のない旧データは保守的に扱い、欠けた通常リンクの返却規則、required先の失効、出典と実入力の連鎖を先に定義する必要があります。

## 3. 原子的な編集の単位が、生成物の依存単位にもなる

`src/client/memory.ts` の `edit` は、全入力をmergeし、全出力に同じmanifestを付けます。`src/client/retrieval.ts` の `compatible` はその前提を検証します。

Aから結論a、Bから結論bを一つのeditで作り、Aだけ改訂する再現例では、a/bの両方がstaleになりました。別々のwriteで作ると、aだけがstaleになりbは返ります。Memory/SQLiteで一致しました。

同じモデル呼出しでA/Bを見せたなら、両出力の依存を広く取ることには理由があります。しかし、**同じコミットに入ったことだけでは、同じ生成入力を見た証拠にはなりません。** 大量の独立入力をagenticに処理して一括保存したい要件では、この結合が問題になります。

**改善の判断：入力を観測した単位はホストが記録し、保存の原子性とは区別できるようにする。** モデル自身の引用リストで依存を狭める方法は採りません。最初は独立したホスト入力scopeを用いた比較を行い、その結果を同じtransactionへ確定する最小の契約を設計します。人格、専用Writerサービス、別の意味メモリ型は不要です。現在は同一editの全入力依存を維持します。

## 4. 取得計算で参照したものと、返した本文が同じ記録に入る

`Engine.get/record/view` は取得時のrevisionをTraceへ入れます。検索候補の検証、グラフ探索、リンク参照先も含まれます。`read` の返却本文だけを記録しているわけではありません。

12候補から本文1件を返す `depth: 0` の再現例で、receiptの元のTraceには12版が記録されました。**「モデルが12件の本文を読んだ」と説明するのは誤り**です。一方、選択計算が12件に依存したことは事実です。

改善では「取得を再現する依存」と「生成モデルへ渡した入力」を契約上区別します。同じmanifest内で意味を明記するところから始め、別の監査システムを増やす必要はありません。今ある記録を返却本文のみに切り詰めると、検索の否定結果や選択への依存を失うため行いません。

今回、公開readのTraceと、確定出力用のmanifestの役割は残しました。 読み取るだけで出力を作らないeditには、永続的な生成依存manifestを作らないようにしました。返却しないコミット用Traceをmanifestと丸ごと二重に保存する処理と、どこからも参照されない記述属性を取り除きました。既存manifestの余分な属性は読取を妨げず、実入力・query範囲・権限・expiryによる検証は維持します。実際に観測した保存位置である `watermark` は監査情報として残し、保持snapshotを意味しない旧 `snapshotToken` と区別しました。既存の二重保存行の一括削除はしていません。

## 5. 残る旧概念を、新しい機能として育てない

- 保存契約の `include` はpinnedかつ非循環を要求しますが、公開 `links` は一般のreferです。旧includeを読む必要があることと、新しい階層型をユーザーへ要求することは別です。新規の必須本文には `required` が既にあります。
- `validTime` は検証・保存されますが、公開操作が時間方針を実行するものではありません。自動失効や記憶減衰の設定を足す理由にはしません。
- `organization/derived/hypothesis` は現在、異なる検索アルゴリズムを持つ型ではありません。sourceの取込権限と、extractionの原文一致処理には実際の差があります。分類名の数と必要な信頼・引用契約を分けて整理します。
- 内部 `WriteRequest.guards` の個別head/query-observation経路は、現行clientが常に空配列を渡す旧経路です。現在の競合検証の本体は `expectedHead` と入力manifestです。query範囲の検証能力そのものは必要なので、契約を削る際に `queryGuards` の保証まで取り除かないよう区別します。
- `MemoryClient` の生成署名と `forExecution` の型が内部 `Engine/Trace` に触れるため、完全な内部型隔離にはなっていません。ただし型exportを隠すこととJS実行の権限境界は別です。別パッケージや汎用plugin機構へ分割する必要はありません。

`source` はホストが取り込んだ原資料という由来であり、正しい事実という認定ではありません。`required` の保証も、宣言された条件の同梱です。Writerが宣言しなかった例外まで自動的に発見したことにはしません。

保存済み版を読めることは必要です。互換表現を新たな概念として教え続ける必要はありません。次の破壊的変更では、既存データの読取・索引再作成・削除を試したうえで、不要な新規書込経路から縮めます。

## 6. 数学的な核を、特定の高速化へ固定しない

同じ版を複数のまとまりで共有する場合は一変数ですが、旧版へのpinnedリンクと新版へのlogicalリンクは別の情報を指します。実装のランキングはrevision IDを使います。研究fixtureの領域割当とwarm対応はcurrent headのみの構造を前提にしており、複数版が同時に現れる一般グラフでの対応は別途検証が必要です。論理Atom IDだけで旧版と新版をまとめないことを契約に含めます。

v0.5の有限PPR、収束先の線形解、Schur消去、本文パッキングは異なる研究評価です。v0.6 runtimeの実行規則は候補グラフを固定した単一の `a = D(h)m + Tᵀa` です。研究で消去順序が違っても同じ解になることは、親Atomの追加・意味の再要約でも順位が不変になることを意味しません。複数の意味関係が同じAtomへ入る効果は、実装による実体の複製と区別します。

合成実験は先にグラフを取得してから数値復元を省略しています。1024ノードまでの密な準備計算にも上限があります。「本文を開かず計算した」と「storageからノードや辺を取得しなかった」は別です。今後は候補取得、グラフ取得、係数準備、失効検証、数値評価、本文返却の費用を分けて比較します。

PPRを使う記憶検索には[HippoRAG 2](https://arxiv.org/abs/2502.14802)、ブロック消去と動的更新には[BEARS/BEARD](https://pure.kaist.ac.kr/en/publications/random-walk-with-restart-on-large-graphs-using-block-elimination/)という先行があります。これらの名称を組み合わせたことを独自性の根拠にはしません。Atom Memoryで検証する対象は、共有・更新される構造から、限られた費用で条件付きの本文集合を返せるかです。

## 改善の順序と採否

1. 今回の未使用契約・重複保存を除き、依存の説明を実装に合わせる。
2. 意味構造を評価質問を見る前に固定し、入口の取り逃しと返却選択の失敗を分けて測る。親が答えの例、子が答えの例、否定・例外・多重所属、疎/密/更新の多いグラフを含める。6問に合わせてseed数やweightを調整しない。
3. 条件閉包と共有引用を含む返却集合の選択を、現在のgreedyと同じ予算で比較する。説明メタデータの削減も、必要な関係・出典を落とさない条件で評価する。
4. 入力scopeと原子的コミットを区別する契約、関連と削除依存を区別する契約をそれぞれ検証する。旧データの依存を推測で狭めない。
5. 同じ返却契約を実現する評価器として合成計算を再比較する。取得全体で利点がなければ採用しない。

返却選択の改善を、Writerの意味品質が改善した証拠にはしません。正しい構造で効くことと、AIが全履歴からその構造を育てられることは、別の評価です。

## 活性入力の提案に対する追加検証

状態：v0.6で利用活性を実装済みです。`recordUse` / `resetUse` は信頼されたホストのAPIで、利用状態は主体・policy・revisionごとに保存し、Coreの評価へ接続します。以下では v0.5 の研究データをベースラインとして明示し、現行の数値契約と反例を分けて記録します。

### 核として必須の活性化

利用の通知・蓄積・減衰から初期活性を作り、関係を通して伝播する機能をライブラリの核に含めます。外付けの最終score補正や任意pluginとして扱いません。受理された利用がなければ `h = 0` として本文一致だけの初期活性になります。利用統計はAtomの本文・所属・全利用者共通の属性にはせず、認証主体・policy・revisionに対応する補助状態として保持します。

ライブラリが検証する核心は、有限・非負の入力と、宣言された増幅上限です。何を利用と認めるかはアプリが判断し、信頼されたホストが対象・主体・policy・revisionを確定して通知します。ライブラリは受理した利用の集計・減衰・初期活性への変換を担います。自動readへ出たこと、探索・伝播で触れたこと、数値評価を再試行したことだけでは加算しません。成功したモデル応答後のホストackだけが利用イベントです。

既定値は半減期7日、最大増幅 `β = 0.3`、伝播 `α = 0.5` です。利用状態は `h` と更新時刻を持ち、`h(t) = h(t0)·2^(-(t-t0)/H) + 1` で一意に更新します。初期ベクトルは `b = D(h)m`、`D_ii = 1 + βh_i/(1+h_i)` です。同じイベントの重複は永続マーカーで抑止し、時計が戻っても追加減衰を起こしません。任意のdecay/gain callbackは公開契約にしません。

### 現行の収束先と接続できる

`P` を各始点で正規化し、行き先がない行は0、`T = alpha P` とします。行和に一様な上限 `rho < 1` があれば、`a = b + Tᵀ a` は有限グラフ上で一意な解を持ちます。一般にはスペクトル半径が1未満という条件で足りますが、行和上限は検証しやすい十分条件です。v0.6 runtimeは符号付き残差を優先度付きで補正し、外向き丸めで計算した誤差上限と `maxEvaluationWork` の予算で停止します。

係数は `propagation * normalizedWeight` を倍精度で計算し、和と積の下限・上限を外側へ丸めます。丸め後の各出辺和から `rhoUpper` を求め、`rhoUpper >= 1` または有限な収縮を証明できない near-unit のグラフは `INVALID_INPUT`（Activation contraction is unprovable）として拒否します。これにより、誤差証明を無視して強い伝播を実行する経路を作りません。

`a = (I - Tᵀ)⁻¹ b` を全成分の合計で正規化したものは、v0.5研究で使ったseedへdangling massを戻すPPRの収束先と一致します。これは既定の32反復で停止した中間値やbit単位の一致ではありません。v0.6では本文一致と利用活性から `b = D(h)m` を作り、同じ線形解へ渡します。

### 生の上限と正規化後の上限は異なる

固定グラフで `m <= b <= (1 + beta)m` なら、非負の伝播から `a_base <= a_boost <= (1 + beta)a_base` が成り立ちます。正規化後は、非ゼロ入力について次の範囲になります。

```text
r_base / (1 + beta) <= r_boost <= (1 + beta) r_base
```

分子の増幅と全体のmassの増幅をそれぞれ評価すれば導けます。全成分の値が上がる保証ではありません。関係がない二つのAtomでも、`[1, 1]` を `[1.3, 1]` にすると正規化値は `[0.5, 0.5]` から約 `[0.5652, 0.4348]` へ変わります。beta=0.3の例は最適値という意味ではありません。

120個の固定グラフで生の範囲、正規化後の範囲、danglingを含む現行PPRの十分収束した結果との比較を行い、最大差は約 `9.34e-14` でした。これは小規模な倍精度計算の確認で、意味品質やすべての浮動小数点入力の保証ではありません。

### 保証を守るには、グラフを変えない

増幅をtop-k seedの選別前に行うと、候補集合が変わります。1 seedだけ採る例で、素の一致 `[1, 0.9]` はAを採り、30%以内でBを増幅した `[1, 1.17]` はBを採ります。切り詰め後のBは0から1になるため、前のゼロ値に対する乗法上限を満たしません。

同じseed集合でも、増幅後の順に探索してノード・辺の上限で止めれば、取得グラフが変わり得ます。初版の比較では、素の一致で認可・鮮度検証済みのグラフを取得・固定した後、その中の初期活性だけを増幅して評価します。現行実装なら `collectRanking` と `finishRanking` の間が検証用の境界です。切り詰めで落ちたAtomは、この方策だけでは救えません。発見段階へ活性を使う改善は、別の取得品質比較として扱います。

### 任意のdecay関数は、単一状態で集約できるとは限らない

指数減衰なら、時刻 `t0` における残存影響 `h` から、時刻 `t1` の値へ次で更新できます。

```text
h(t1) = h(t0) * 2 ** (-(t1 - t0) / H) + 今回受理した利用の寄与
```

同じHと重みの定義を保つ限り、数値計算のために全イベントを保持する必要はありません。過去時刻のイベントが遅れて届く場合は、その経過分も減衰してから加えます。重複受理の防止や利用イベントの監査が必要なら、その記録は別途必要です。

一方、`K(age) = 1 / (1 + age)` では、今の1回利用と、1単位前の2回利用は、現在の `h` がともに1です。1単位後はそれぞれ1/2と2/3になり、一つの `h` と時刻から区別できません。任意のカーネルまで提供するなら、追加の履歴または近似契約が必要です。

v0.6は、半減期7日・最大増幅 `β = 0.3` の指数減衰＋有界な飽和増幅を標準にします。`maxBoost` の変更では状態をリセットしませんが、半減期の変更は `STATE_INVALIDATED` として明示的な `resetUse` を要求します。任意のdecay/gain callbackを公開契約にせず、必要な新しい規則は別のスキーマと移行として評価します。

### 時刻・利用・権限・返却を混ぜない

- 減衰の時刻 `t` と伝播の反復 `k` は独立です。同じ時刻・利用入力なら、反復を増やしたり部分消去で高速化したりしても、残存利用量 `h(t)` は変わりません。
- 一つのreadとcursor継続では、時刻、利用状態、方策設定を固定するか、変更時に明示的に失効させます。関係の計算表が再利用できても、前の検索結果がそのまま有効とは限りません。
- サーバー・利用主体・共有範囲を越えて利用履歴を混ぜません。活性だけを通して別scopeの利用傾向を持ち込まないことも、入力の分離に含めます。
- 同じ版を複数の親経由で読むことを、複数の独立利用として自動加算しません。実際の受理イベントの単位はアプリが通知します。
- 初版では観測版への利用を基準にし、同じ論理Atomの訂正版への継承はホストの明示判断にします。過去の利用は、訂正後の本文が同じ意味で有用という証拠にはなりません。
- stale・非認可・purge済みの対象を、活性によって復活させません。利用の補助状態を保存する場合も削除対象との関連を保持します。
- 単一の伝播規則は、必要条件の同梱や出力費用の制約を消しません。活性を高くしただけでは、説明Atomが出力枠を占める問題の解決にはなりません。

時間に基づく忘却と強化には[MemoryBank](https://arxiv.org/abs/2305.10250)、PPRによる連想検索には[HippoRAG 2](https://arxiv.org/abs/2502.14802)、利用の新しさと頻度を活性として扱う発想には[ACT-R](https://act-r.psy.cmu.edu/wordpress/wp-content/uploads/2012/12/39jra_cds_2000_a.pdf)という先行があります。本案の式やカスタマイズ性だけを新発明とはしません。

研究する対象は、内容・利用・時間から生じる初期活性を、共有・再帰構造の上で合成・再利用し、本文と条件を有限予算で返す具体的な評価規則です。同じ条件での正確さ・探索費用・更新費用・出力品質に差があるかを検証します。利用による補正が本文選択やWriterの意味品質を改善するかは、数値上限とは別の評価です。

再現は `node research/architecture/activation.mjs`。記録は `research/architecture/activation-results.json`。保存する場合だけ `--record` を付けます。これは v0.5 の研究ベースラインで、v0.6 runtimeの利用イベントAPI・利用状態ストア・評価器そのものではありません。

### 最小実装の受入条件

| 確認すること                                | 必要な結果                                                                  |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| 自動readだけを繰り返す                      | 利用状態が増えない。検索結果を次の利用入力へ自動還流しない。                |
| アプリが受理した利用を通知する              | 対応する主体・スコープ・版の利用状態だけを更新し、初期活性に反映する。      |
| 同じ利用イベントの再送                      | 一度の受理として扱い、回数や強さを二重加算しない。                          |
| 別の主体・サーバーから同じAtomを読む        | 利用履歴を共有する明示契約がなければ、相手の利用補正を受けない。            |
| 同時刻で反復数や評価方式を変える            | `h(t)` が同じ。スコア差は定義された数値評価の誤差として扱う。               |
| 同じ時刻・利用状態・グラフを再評価する      | 初期活性が同じ。循環や多重所属で利用イベント自体を複製しない。              |
| 時刻が進み、利用がない                      | 指数減衰によって利用の上乗せが基準へ近づく。本文・意味構造は書き換えない。  |
| 半減期を変更する                            | 古い集計値を新しいHで集計済みと偽らず、再集計・リセット等の明示契約に従う。 |
| 高活性の対象がstale・非認可・削除済みになる | 現在の検証と削除の規則が優先される。必須条件を省略しない。                  |

これらは v0.6 の受入条件です。Memory/SQLiteの利用状態・重複抑止・認可・purge・時計後退の回帰を `test/activation*.test.mjs` で確認します。意味品質や実モデルの改善は別の評価です。

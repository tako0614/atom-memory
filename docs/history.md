# 長期間の履歴をWriterで整理する

大量の履歴は、有限の入力範囲ごとにAIが既存の記憶を調べ、情報・まとまり・関係をまとめて編集します。1 Atomごとにモデルを呼ぶ必要はありません。Atom MemoryはJavaScriptライブラリなので、実行タイミング、履歴の取得、ジョブの進捗、モデルと費用は呼び出すアプリが管理します。

## 入力の区切りと意味のまとまりを分ける

アプリは会話・資料の区切り、件数、バイト数を使って、モデルへ渡せる有限の範囲を選びます。日付や月は取得範囲として使えますが、それをそのまま話題の分類にする必要はありません。AIが内容を見て複数の話題へ分け、以前のまとまりへ追加し、説明を改訂できます。

同じ情報を複数のまとまりから参照でき、まとまり同士もAtomで結べます。大きな集合の全メンバーを一つの本文へ書き直す代わりに、`group` / `member` などの役割を持つ関係Atomを追加します。数か月後の訂正も、元の発言を残して訂正の関係と新しい説明を保存できます。

一回の範囲について、Writerは `search` → `inspect` / `resume` → `batch` を必要に応じて繰り返します。各モデル呼び出し前には、現在のcontext・明示的なthought・直近の観測に合わせて記憶を選び直します。埋め込みを設定するとベクトルを使います。非公開のモデル内部思考を取り出す機能ではありません。

## 複数Atomを一度に編集する

モデルアダプターは次の `ModelAction` を返せます。`m1` はその実行中に取得した原資料の参照名です。

```json
{
  "kind": "batch",
  "operations": [
    {
      "kind": "write",
      "as": "topic",
      "content": "招待機能の設計についての議論",
      "sources": [{ "ref": "m1" }]
    },
    {
      "kind": "write",
      "as": "fact",
      "content": "Aliceは招待リンクを24時間で失効させると提案した。",
      "sources": [{ "ref": "m1" }]
    },
    {
      "kind": "write",
      "content": {
        "text": "Aliceの期限案は招待機能の議論に属する。",
        "links": { "group": "$topic", "member": "$fact" }
      },
      "sources": [{ "ref": "m1" }]
    }
  ],
  "output": { "processed": true }
}
```

- `operations` は `write` / `revise` / `retire` / `supersede` の配列です。既定で最大64操作。ホストの `maxBatchOperations` で1〜1,000の範囲に設定でき、出力トークンや編集全体の予算も適用されます。
- `write` / `revise` の `as` は、そのbatch内の後続操作から `$名前` で参照できます。英字で始まる64文字以内の英数字・アンダースコアを使います。前方参照と同じ名前の再定義はできません。
- `output` を付けるとその応答で実行を終了し、編集全体を確定します。付けなければ次のモデル呼び出しへ進み、操作結果に新しい `mN` 参照が渡ります。`$名前` は次のbatchには持ち越しません。
- `commit: 'edit'` の実行で使用します。一連の編集は一つのdraftにあり、最後の操作や後続ステップが失敗した場合も全体を取り消します。read-onlyの実行では書き込みできません。

## 過去の整理を維持する

履歴の構造化にはホストから `harness.run({ ..., commit: 'edit', basis: 'historical' })` を指定できます。これは既存の `memory.edit` の過去資料向け設定と同じです。入力資料の版を記録し、新しい資料が増えたことだけを理由に過去の整理を現在の結論へ置き換えません。改訂対象の競合、資料へのアクセス権限、purgeの扱いは維持します。モデル自身がこの設定を変更することはできません。

既定の `basis: 'current'` は現在の情報に依存する判断向けです。過去資料の整理は現在の事実の保証ではありません。後から届いた訂正はWriterに渡して整理を更新します。

## 長く動かすときの進捗と費用

各範囲を完了したらアプリが処理済みの入力ID・世代を記録し、次の範囲を渡します。`MemoryHarness.run()` 自体にはプロセスをまたぐ再開やジョブのexactly-once保証はありません。モデル応答後・確定後・索引更新後の失敗を区別したい場合、そのチェックポイントはアプリに置きます。未読ページや途中で切れた範囲を、期間全体の処理完了として扱わないでください。

ベクトルを使う場合は確定済みの `result.changes` を `host.indexAtoms()` で優先索引化し、`host.updateIndex()` で残りの変更と直接参照元を追いつかせます。入力をすべて書き終わるまで待つ必要はありません。[索引更新のAPI](/adapters)を参照してください。

バッチ化で減らせるのは、主に繰り返す指示・検索・通信の費用です。必要な原文や出力のトークン量は残ります。件数を増やすだけでは読み落としや出力切れが起き得るため、入力サイズ・出力予算・`maxSteps` を組み合わせ、実際のモデル利用量と整理品質を測ります。ライブラリのトークン予算と、アプリ側の通貨による予算は別に管理します。

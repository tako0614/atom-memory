# アーキテクチャ

Atom Memoryは、情報と関係を版付きで保存し、文脈に必要な本文を、その解釈に必要な条件と出典とともに予算内で返すNode.js / TypeScriptライブラリです。

Atomの本文・関係・出典・版が正本です。埋め込み、順位、返却集合、計算キャッシュは派生物です。読むたびに意味上の関係を書き換えたり、タスク成功率を使って保存構造を自動再編したりしません。

## 三つの責務

```text
Agent / アプリ
  内容理解、入力選択、生成モデル、Writer、ジョブ、費用、採用判断
                  │
       read / search / inspect / write / edit
                  │
記憶の読取と編集
  候補発見 → 入力の鮮度検証 → 関係の評価 → 条件を伴う本文の返却
  非公開の編集 → 前提の検証 → 原子的な確定
                  │
版付きAtomの保存
  本文、役割付き参照、出典、入力記録、認可、CAS、削除失効
                  │
            Memory / SQLite
```

これは責務の区別で、三つのサービスや別パッケージを要求しません。索引更新の操作はライブラリが持ち、いつ・どの範囲で呼ぶかはアプリが決めます。埋め込みproviderの呼出しは検索の一部で、使用量と中断を管理します。文章生成のループは持ちません。

## Atomについて保証すること

| 契約           | 保証の範囲                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 一つの形式     | 本文、まとまり、関係を同じAtom形式で保存する。通常の二項関係は役割付きリンクでよい。                   |
| 共有           | 複数の親から同じAtomの同じ版を共有できる。同文の別発言や異なる版を自動統合しない。                     |
| 一般グラフ     | 木に限定せず、再帰・多重所属・一般リンクの循環を扱う。                                                 |
| 不変版         | `revise` は同じ対象の新しい版を作る。observed参照は元の版、logicalリンクは読取snapshotの版を解決する。 |
| 本文の直接索引 | 子の本文を親へ暗黙連結しない。リンク経由の寄与は構造評価で扱う。                                       |
| 条件付き返却   | `read` は `required` と宣言された本文を含めた束を詰める。収まらなければ主張を返さない。                |

Atomは数学的に唯一の最小意味単位ではありません。粒度、関係名、重複の意味的な整理はWriterが原資料に基づいて決めます。同じ形式で保存することは、すべてのAtomを同じ返却価値で扱うという理論ではありません。

## 五つの操作

`search` は候補を順位付きで探す操作、`inspect` は指定版と関係を調べる操作です。`read` は本文・条件・出典をコンテキスト予算内で組み立てます。`write` は追加、`edit` は複数の追加・改訂・retireを非公開で準備し、前提を検証して一括確定します。

現在の `read` は `search` と同じ構造ランキングを用い、上から条件の束を詰めます。関連度の高い説明が有用な本文の返却を妨げる場合があるため、返却集合の選び方は改善対象です。順位は真偽や絶対的重要度を表しません。[ランキング](/ranking)と[設計レビュー](/design-review)に評価と限界を記録しています。

## 鮮度と履歴

`read/search` は保存済み生成物の入力の版とquery観測を検証します。staleな生成物はseedにも本文にも採用せず、`stale` に参照を返します。古い候補のscoreを現在の原資料へ移すことはありません。原資料は自身の本文一致や構造探索から独立に候補になります。

ライブラリは古い入力から新しい意味を生成しません。アプリが入力を選び直し、Writerを実行して通常の `edit` で改訂します。`inspect` は古い生成文を調べるためにも使え、現在の回答として有効であることを保証しません。

一つの旧版を指すことと、周辺全体を過去の同時点へ戻すことは別です。後継の採用、保持期間、いつ履歴を再整理するかはアプリの責務です。[改訂と履歴](/concepts)を参照してください。

## 入力記録と削除

入力manifestは、取得計算が参照した版、現在性の前提、query観測、出力の所属、認可、historical basisを保持します。取得した候補や関係先も含むため、「モデルに渡した本文だけの一覧」ではありません。出典の引用範囲とも区別します。

現行の `edit` は全入力を全出力の依存単位にします。purgeは出典・任意リンク・入力記録をたどって依存物を連鎖削除します。保守的な保証ですが、原子的な保存と生成入力、通常の関連と導出依存が結合しているため、共有構造が大きいほど影響が広がり得ます。[設計レビュー](/design-review)に両adapterでの再現例と変更条件を示します。

役割weightを0にしても保存上の依存は消えません。認可・出典・削除は検索のweightで変更する方針ではありません。削除依存を狭めるには、モデルの自己申告に頼らないホスト入力契約と、既存データの扱いを定義する必要があります。

## 計算と意味の保証を分ける

候補の取り逃し、未取得の辺、選んだグラフ上の数値誤差、Writerの関係の誤りは別問題です。有限の取得結果を返し終えたことは、全資料の網羅を意味しません。`coverageCertified` は常に `false` です。

[合成評価](/composition)は内部消去・復元・再利用を比較する研究実装で、既定評価器ではありません。同じ固定グラフでの数値一致と、意味構造を変更しても順位が変わらないことは別です。計算方式の採用には、本文取得まで含めた効果を要求します。

保存済み版の互換性と、索引の再生成は別に管理します。旧表現・scopeごとの索引準備と旧保存フィールドの扱いは[移行](/migration)を参照してください。

## 次の実装で必須にする活性化

内容・受理された利用・経過時間から初期活性を作り、共有・再帰構造の上で同じ伝播演算を使う方針です。利用の蓄積・指数減衰・上限付き増幅はライブラリの核に含め、何を利用と数えるかはアプリが通知します。自動readや探索だけでは加算しません。

利用統計は認証主体とスコープに対応する補助状態であり、Atomの本文や全利用者共通の重要度にはしません。減衰の時計と伝播反復は独立です。鮮度・権限・削除・必須条件の保証は活性によって上書きしません。

これは確定した実装方針です。利用イベントAPI・利用状態の保存・検索への接続は未実装で、現行の五操作にその機能があるという意味ではありません。[設計と最小実装の受入条件](/design-review)に、数値的な保証、候補打切りの制約、カスタム減衰の費用、新規性の検証対象をまとめています。

## 実装の所在

| 責務                           | 実装                                            |
| ------------------------------ | ----------------------------------------------- |
| 操作と原子的な編集             | `src/client/memory.ts`                          |
| 認可・参照・入力記録・候補取得 | `src/client/engine.ts`                          |
| 鮮度検証・条件閉包・本文構築   | `src/client/retrieval.ts`                       |
| グラフ取得と数値ランキング     | `src/client/ranking.ts` / `src/core/ranking.ts` |
| 確定・出典検証・purge          | `src/core/store.ts`                             |
| 索引更新と保存実装             | `src/client/indexing.ts` / `src/adapters/`      |

公開APIは[操作一覧](/api)、現在の改善判断は[設計レビュー](/design-review)を参照してください。

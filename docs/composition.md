# 合成可能な連想評価の研究

Atomの共有・再帰構造を、検索計算の合成単位として使う研究用の実装を比較しています。v0.7の既定 `read/search` は利用可能性 `u` と本文一致 `m` から `b = m(1 + βu/(1+u))` を作り、符号付き残差を使う単一の `a = b + Tᵀa` 評価器です。Schur消去は採用していません。`research/composition/reference-ranking.mjs` の凍結v0.5参照実装は、回帰比較専用です。

保存する意味構造、5つの公開操作、本文の直接埋め込み、版、認可は維持します。内部の計算表を新しいAtom型にせず、Writerやモデル実行をCoreへ戻しません。

## 実装して比較したもの

- 共有点を一変数に保った内部消去と復元。
- 文脈・関係変更の残差補正と数値係数の再利用。
- 未復元候補の上界と、復元・出力費用に基づく詳細化。
- 本文・必須条件・引用の共有を含む逐次パッキング。
- 合成評価、全体の分解、フラット評価、local-pushの同予算比較。

研究のパッキングは現行の本文・条件・出典契約へ接続して比較しますが、runtimeの数値評価を置き換えません。候補の出力順と、条件一式が収まらなければ主張を返さない契約は維持しています。公開APIは増やしていません。

## 採用を見送った理由

小規模な固定グラフでは、十分収束した参照計算と数値誤差の範囲で一致しました。Memory/SQLiteで、確定した出力の本文・出典が一致し、条件欠落もありませんでした。

ただし、合成評価が常に速いわけではありません。グラフ取得は引き続き全量で、その費用が大きいままです。数値復元の省略を、取得全体の省略とは呼びません。

v0.5の研究ベースラインとして、日本語の合成資料97 Atom・6問を実際の多言語埋め込みで評価すると、seedを広く取った場合に説明Atomが出力枠を占め、必要な根拠を返せない例も確認しました。これは全評価方式に共通しました。入口選択・正規化・返却内容の問題を、計算方式の高速化と分けて扱う必要があります。

## 記録と再実行

ソースリポジトリの `research/composition/README.md` に契約・限界・測定結果をまとめています。研究用の数値評価器、モデル実行コード、保存済み埋め込みはnpm配布対象に含みません。

```sh
npm run build
npm run check:research
node research/composition/evaluate-reader.mjs
node research/composition/evaluate-semantic.mjs
```

後者は保存済みの実埋め込みを使い、有料モデルを呼びません。これは合成データによる限定的な試験であり、実際のコミュニティ全体やAI Writerの意味品質を保証するものではありません。

# 0.10候補：探索実験と採否

判定：**今回の活性順方式は既定へ採用しない。npmは0.9.0を維持する。**

実装・比較・不変条件の検証を行った。今回の方式は、公平な配分だけの方式を上回る必要根拠の表示改善を示さず、途中の数値評価が費用を増やした。これは「活性を探索へ利用する方式は全て無効」という結論ではない。この具体的な試作を公開版へ採用する根拠が不足しているという判断である。

## 測定条件

- 15個の固定構造、80 Atom、同一の固定4次元ベクトルと初期候補。本文索引・Engine・検証・スコープ・実際の本文選択器を通す。
- 各構造に10予算条件、6方式、Memory/SQLite、独立した保存状態で3回ずつ。合計5,400回、集計1,800行。
- 初期候補のみ、v0.9の実collector、活性順のみ、配分のみ、配分＋同じ暫定評価、配分＋活性順を比較する。最後の二つは暫定評価をそろえ、探索順だけを変える。配分のみは、計算費用を抑える実用上の対照として別に残す。
- quality条件は候補256、bytes 262144、本文32件、context 8000、評価/packingそれぞれ200000。取得件数8/16/32/64、評価2000/20000の一軸ずつの制限も、全構造へ同じ規則で与える。元の表示/計算が厳しい3条件はstressとして残す。
- 実際の出力はUTF-8 byte tokenizerで数える。初期の小さい予算では参照表示付き本文が一件も入らなかったため、比較前に共通quality予算を追加した。方式別・ケース別に結果を見て予算を合わせてはいない。
- 各fixtureで受理済み利用を一度用意し、同じ評価時刻と保存状態を各方式へ複製する。絶対時刻のある利用集計のため、再実行間では微小な数値差があり得る。各run内の3回は候補・表示・ledger使用量の一致を確認する。
- 各取得のwall timeには候補取得、同期transaction、検証、暫定/最終評価、packing、receipt作成を含む。表はfixtureごとの3回の中央値の合計。索引準備は別欄で記録し、保存状態の複製と独立oracleは測定外。

## 結果

quality条件の15ケースでは、関係探索を行う方式は全て同じ根拠集合を返した。

| 方式                           | 必要根拠を全て表示 | 評価 work 合計 | Memory ms | SQLite ms |
| ------------------------------ | -----------------: | -------------: | --------: | --------: |
| 初期候補のみ                   |               3/15 |          1,056 |     11.36 |     21.78 |
| v0.9 FIFO                      |              15/15 |         66,576 |     37.07 |     85.68 |
| 活性順のみ                     |              15/15 |        322,477 |     77.47 |    164.10 |
| 一巡の配分のみ                 |              15/15 |         73,184 |     51.25 |    113.63 |
| 配分＋暫定評価（順序は登録順） |              15/15 |        313,898 |     77.26 |    160.49 |
| 配分＋活性順                   |              15/15 |        314,598 |     78.00 |    170.44 |

評価 workはライブラリの計上単位でありCPU命令数ではない。短い合成fixtureの時間を、一般的な本番性能へ外挿しない。

全150予算条件の比較は、両保存アダプターで同じ傾向だった。

| 配分＋活性順の比較相手 | 表示根拠が増えた条件 | 減った条件 |
| ---------------------- | -------------------: | ---------: |
| v0.9 FIFO              |                    1 |         11 |
| 配分のみ               |                    0 |         10 |
| 同じ暫定評価＋登録順   |                    0 |          0 |

FIFOを上回った一件は循環・多重経路で候補予算16の条件だったが、配分のみでも取得できた。途中の再評価を追加する積極的な理由にはならない。評価予算が小さい場合は、最終評価の費用を残すため関係探索を早く終了し、根拠の取得が減った。

初期候補のみのquality結果は3/15。数値グラフから取得した根拠は2/15だが、必須条件の閉包が別に本文を取得するケースがあるので表示結果は3/15となる。取得済みグラフ、必須条件の取得、実際の表示を同一視しない。

必須条件を省いた表示は0件。ただし空の結果も含むため、これだけで取得率や出力品質が高いとは評価しない。数値評価が収束した行の独立oracleとの差は最大約1.76e-7。予算不足で未収束の行はより大きな誤差を持つが、全行で報告した誤差上界内にあった。この上界は取得済みグラフだけを対象とする。

## 実装と修正した不具合

`collector.mjs` が有限のslot/posting処理、最小深さの修正、一巡の割当て、直接seed、暫定評価の再利用、最終評価の予約を持つ。`harness.mjs` は同じ実Engineの候補取得とpackingを使い、全phaseのledger合計を検証する。公開APIや本番collectorを切り替える設定は追加していない。

検証中に、終了済みの探索先を含む一巡で再帰が終わらない不具合、未知の逆引き元の取り込み、暫定評価の上限を越えた後のgraph変更、比較に含める費用の不一致を修正した。後から短い経路を発見したとき、depth capで閉じていたAtomを開き直して子へ到達することも、長い経路が実際に先に来る専用例で確認した。

逆方向重み0のfixtureは、初回点検で「新しく発見するAtomの直接seed」を試しておらず、零活性の別Atomを根拠とする向きになっていた。最終測定前に、入口への逆引き元が直接文脈へ一致する形へ修正した。全方式へ同じ修正を適用して再測定しており、順位方式に合わせた調整ではない。

`src/client/activation.ts` と `ranking.ts` には内部用の任意の評価時刻を追加した。省略時の公開版の挙動は変わらない。指定時刻より新しい利用状態は拒否し、時刻だけから過去の状態を再現できるとはしない。deadlineは実時間のまま。

## 限界と次の判断

今回のcollectorは不変のfixtureと同期transaction、取得用の子ledgerに依存する。非同期providerや別プロセスの利用更新へ対応する一般的なsnapshot、全コーパスtop-k保証、実ANNの取り逃し、LLM回答品質、実際のDiscord全履歴は検証していない。別request間のwarm遅延も測定していない。再利用を測ったのは、一回の探索中にgraphが増える際の暫定解である。

次に研究するなら、毎回ほぼ全体を再評価する費用を抑え、安い配分だけの対照を同条件で超える必要がある。今回の結果を理由に、新しい公開スコアや学習機能を足さない。索引・候補発見・並行snapshotが未完成の状態で0.10として既定公開もしない。

## 再現

```sh
npm ci
npm run check:v010
npm run evaluate:v010
```

`results.json.gz`（gzip圧縮したJSON） に各方式の取得/表示したID、全資源のphase内訳、予算、数値誤差、時間の3標本、準備費用、実験コードのSHA-256を保存している。例を絞るには `node research/v010/evaluate.mjs --fixture cycles-and-multiple-paths --budget candidates-16 --repeat 3 --output /tmp/cycle.json` を使う。
